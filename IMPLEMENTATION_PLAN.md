# GitHub Push Event Ingestion Service — Implementation Plan

## 1. Purpose

Build a production-minded, locally runnable Ruby on Rails service that polls GitHub’s Public Events API, processes `PushEvent` records, retains raw and structured data in PostgreSQL, enriches actors and repositories, and remains recoverable across application and worker crashes.

The implementation will prioritize:

- Correctness and durability
- Clear separation of responsibilities
- Idempotent and restart-safe processing
- Predictable GitHub API usage
- Simple local operation through Docker Compose
- Observable system behavior
- Focused tests for important failure modes
- Small, understandable pull requests

The delivered implementation will satisfy the required public-events source while preserving an extensible event-source adapter for future GitHub Events API endpoints.

## 6. Event-Source Design

The required delivered source will call:

```text
GET https://api.github.com/events
```

The source adapter will isolate endpoint construction and source-specific state from common event processing.

The event processor registry will initially support only:

```text
PushEvent
```

The application may expose configuration such as:

```text
GITHUB_EVENT_TYPES=PushEvent
```

Configured event types must be validated against implemented processors. Unsupported types should fail fast with a clear configuration error.

A future repository source can use:

```text
GET /repos/{owner}/{repository}/events
```

without rewriting persistence, enrichment, or the push-event processor.

## 8. Durability and Crash Recovery

### Durability boundary

A GitHub event is considered accepted only after its `push_events` row is committed to PostgreSQL.

### Processing sequence

1. Fetch a page from GitHub.
2. Validate the response.
3. Filter `PushEvent` entries.
4. Normalize required attributes.
5. Insert raw and structured records idempotently.
6. Commit the PostgreSQL transaction.
7. Schedule enrichment.
8. Reconcile committed events whose enrichment was not scheduled or completed.

### Crash behavior

#### Crash before commit

The transaction rolls back. The event may appear again in an overlapping GitHub poll.

#### Crash after commit

The event remains durable in PostgreSQL. Pending enrichment is rediscovered after restart.

#### Worker crash before enrichment commit

The job is retried.

#### Worker crash after enrichment commit but before acknowledgement

The job may execute again. Idempotent upserts produce the same durable outcome.

### Processing semantics

The system provides:

```text
At-least-once execution
+
Idempotent writes
+
Unique constraints
=
Effectively-once persisted outcomes
```

The system does not claim exactly-once execution.

### Docker persistence

PostgreSQL will use a named Docker volume. Normal container stop, restart, crash, recreation, or `docker compose down` must not remove stored events. An explicit volume deletion is treated as an intentional destructive reset.

## 9. Polling, Pagination, and Concurrency

### Pagination

- Request `per_page=100`
- Keep maximum pages per polling cycle configurable
- Default to no more than the API’s useful bounded window
- Stop when:
  - an already-known event boundary is reached
  - no next page exists
  - an empty page is returned
  - the configured page cap is reached
  - the rate-limit reserve is reached

### Polling state

Persist per source:

- ETag
- next allowed poll time
- last successful poll time
- consecutive failure count
- rate-limit state

### Multiple poller containers

Multiple poller or worker containers must not cause the same source to be polled concurrently.

Use:

- Job concurrency limits keyed by source ID
- PostgreSQL advisory lock or row-level source claim
- Unique event constraints as final duplicate protection

### Multiple event sources

Each event source maintains independent:

- ETag
- next poll time
- failure state
- source configuration

All unauthenticated requests running behind the same outbound IP share the same GitHub request budget.

## 10. Rate-Limit and Retry Policy

All GitHub requests must pass through a shared request executor.

### Headers to process

- `ETag`
- `X-Poll-Interval`
- `X-RateLimit-Limit`
- `X-RateLimit-Remaining`
- `X-RateLimit-Reset`
- `Retry-After`

### Response behavior

#### `200 OK`

- Process response
- Update source and shared rate-limit state
- Save ETag
- Schedule next poll

#### `304 Not Modified`

- Perform no event processing
- Update polling metadata
- Schedule the next poll using `X-Poll-Interval`

#### `403` or `429` with exhausted quota

- Do not retry immediately
- Defer until the reset time
- Record rate-limited status
- Log remaining and reset metadata

#### Secondary rate limit

- Respect `Retry-After`
- Otherwise use increasing delay
- Stop after bounded attempts

#### `5xx` or network timeout

- Retry a small number of times
- Use exponential backoff with jitter
- Persist failure after attempts are exhausted
- Do not crash-loop

#### Permanent client or configuration error

- Do not retry indefinitely
- Mark the source failed or disabled
- Log actionable details

### Request prioritization

1. Polling for new events
2. Missing repository enrichment
3. Missing actor enrichment
4. Refreshing stale enrichment

Polling receives priority because raw-event capture is more time-sensitive than enrichment.
